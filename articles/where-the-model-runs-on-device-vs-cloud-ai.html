Where the model runs.

A mobile AI feature may use an on-device model, a cloud API or both. Choosing where to run each request means weighing privacy, latency, cost, offline support, battery use and output quality.

By Asım Can Yağız8 September 2026Updated 16 November 202613 min read

The framework

  1. Start with the operation
  2. A matrix with hard constraints
  3. Resolve a route, not a brand
  4. Make local a real service
  5. Make cloud execution narrow
  6. Converge at validation
  7. Design UX around uncertainty
  8. Observe decisions, not users

A consumer app may need to choose between local and cloud execution on every request. A decision made in a design document cannot account for every device, network condition or change in consent.

Consider one user with three devices: a recent phone that already has a system model ready, a tablet that is eligible but still downloading the assets, and an older device that will never run the model at all. Now consider one feature that behaves differently depending on the request: rewriting a sentence is harmless and local, but estimating a price needs current external data. Network, battery, language support, subscription status, and consent can all change between the moment the app launches and the moment the user taps the button.

The route must suit the operation and the device at the time the request starts. It also has to respect the feature's privacy, cost and quality requirements. Those constraints belong in a runtime decision, rather than a compile-time choice that assumes conditions will stay the same.

Start with the operation, not the model

Start by listing what the assistant actually does. Each operation may need a different route:

  • completing a category from the user’s recent history;
  • rewriting one short sentence while keeping its language;
  • grouping a batch of items into buckets the user already defined;
  • interpreting an image and, when needed, consulting live sources.

A rule may be enough to complete a category. A short rewrite is a good candidate for local execution. Grouping can use either route, depending on context size and the required output reliability. Image interpretation depends on device capability; newer hardware may support it locally. Consulting live sources adds a separate need for remote retrieval.

Define the product-level contract once, and put the implementations behind it:

protocol AssistantService: Sendable {
    func rewrite(_ text: String) async throws -> String
    func classify(_ items: [ItemBrief]) async throws -> [Suggestion]
}

struct ItemBrief: Sendable {
    let id: UUID
    let title: String
    let currentGroup: String?
}

Pass a small, immutable, sendable snapshot to this interface. Sharing an object owned by the view or database introduces concurrency and lifecycle risks, and can expose more data than the request needs. Snapshots also let both implementations use the same test fixtures. The button can ask to rewrite text while the service handles model readiness and vendor requests.

Decide with a matrix, and put hard constraints first

I use seven dimensions when choosing a route. Check the ones that can rule out a route before comparing preferences such as cost.

Capability. Can the route even do the job? A local text model cannot satisfy a need for live sources. A cloud text endpoint cannot interpret an image. Keep tool use, supported media, context size, structured-output support, and language coverage in an explicit capability record rather than scattering model-name checks through the code.

Availability. On-device availability is not a boolean. It has states: the OS is too old, the hardware is ineligible, the user has turned intelligence off, the assets are not ready yet, the runtime is briefly busy, or it is available. Cloud availability has its own states: offline, not authenticated, rate-limited, or disabled. Keep those distinctions long enough to choose the right fallback and show the right message.

Privacy and consent. Local execution reduces data transfer, but inputs can still end up in logs, storage or backups. Minimise what a cloud route sends and provide clear, revocable consent for free-form or sensitive content. A fallback must not upload data to a third party unless the user has accepted a policy that permits it.

Economics. On-device inference uses memory, battery and engineering time even though there is no metered network call. Cloud inference has a marginal cost and may require a subscription. Use the operation's cost class when routing: the same button can offer a free local path and a paid cloud fallback.

Latency and lifecycle. Short local work can feel instant once a session is warm; the first call, before that, may not. Cloud calls add network variance but run on far more devices. Either way, the work must be cancellable when the view goes away, and a late result must never overwrite a newer one.

Quality and domain risk. A rewrite and an extracted monetary amount need different standards of validation. Higher-risk outputs may also need human review. Define what counts as valid for the operation before comparing models.

Consistency and operations. Platform updates and device settings can change a local model's behaviour. A provider can change a cloud model. Cloud routes are easier to disable remotely. Local routes can work during a server incident if entitlement and kill-switch checks are cached or permit local operation when the server is unreachable. Both routes need tests and telemetry that identify the configuration in use.

Principle 01

Hard constraints decide which routes are eligible. Preferences like cost and latency only choose among the ones that are left.

Evaluate the hard constraints before anything else. If the operation needs live retrieval, local is out. If there is no consent to upload, cloud is out. If the device model is not ready, local is out for an action that has to happen now. Only after the ineligible routes are removed do preferences like cost and latency decide between what’s left.

Resolve a route, not a brand

Return a decision containing the route, its reason and any permitted fallback. Apply the same eligibility checks to a fallback as to a primary route:

enum Route {
    case deterministic
    case local
    case cloud(tier: Tier)
}

struct RouteDecision {
    let primary: Route
    let fallback: Route?
    let reason: Reason
    let uploadConsentRequired: Bool
}

func resolve(_ op: Operation, env: Environment) -> RouteDecision? {
    if op.canUseRules, env.rulesCanAnswer {
        return .init(primary: .deterministic, fallback: nil,
                     reason: .localRuleMatched, uploadConsentRequired: false)
    }

    if op.localCapabilities.isSubset(of: env.localCapabilities), env.localReady {
        // A cloud fallback is only offered when the cloud route is already
        // allowed, paid for, and consented to — the same three checks the
        // cloud-primary branch makes. Otherwise there is no fallback.
        let cloudFallbackOK = env.cloudAllowed && env.entitled && env.uploadConsent
        return .init(primary: .local,
                     fallback: cloudFallbackOK ? .cloud(tier: .small) : nil,
                     reason: .localCapable,
                     uploadConsentRequired: false)
    }

    guard env.cloudAllowed, env.entitled, env.uploadConsent,
          op.cloudCapabilities.isSubset(of: env.cloudCapabilities) else { return nil }
    return .init(primary: .cloud(tier: op.cloudTier), fallback: nil,
                 reason: .localUnavailable, uploadConsentRequired: true)
}

The local branch offers a cloud fallback only when cloud access, entitlement and upload consent are already present. Checking cloud availability alone would allow a local failure to upload data without consent. In this example, uploadConsentRequired is false for the local primary; a cloud fallback can still be present because consent was checked separately. The resolver also deliberately prefers local execution among eligible routes. It illustrates that policy, rather than implementing every preference in the matrix.

In production, cloudAllowed should fold in a remote kill switch and backend admission, and entitled should not trust mutable client state alone. The decision’s reason is also what feeds privacy-safe telemetry and support later.

Offer automatic, on-device-only and cloud-allowed settings. Store the choice per device, since one person may own devices with different capabilities. In on-device-only mode, hide or disable unsupported actions and explain why. Automatic mode may fall back to the cloud only within the consent and subscription rules above.

Make local execution a real service

Put local execution behind the same protocol as the cloud adapter. Translate its failures into categories such as assets unavailable, context too large, safety guardrail and decoding failure.

A long-lived session avoids repeated warm-up work, but it needs explicit control over overlapping requests. Swift actors are reentrant: an actor-isolated async method can suspend at an await, allowing another operation to enter. Actor isolation alone therefore does not guarantee one response at a time. Stateful session APIs may reject overlapping responses. Use an in-flight flag, a single serial consumer, or a policy that rejects and defers overlapping calls.

Keep the queue bounded. Coalesce duplicate actions, cancel obsolete work and show progress for batches. If a failure may have corrupted the session, discard it and start a fresh one for the next operation.

Validate local output as carefully as cloud output. Extract and decode JSON if the model wraps it in commentary. Trim a rewrite, remove presentation quotes, reject an empty result and treat text identical to the original as a no-op. Grouping results may reference only identifiers included in the request.

The availability states above describe an OS system model, including assets whose download the platform manages. If you deliver your own model, you also own that download. Keep it out of the base install and fetch it when the user opts in, so it does not enlarge the initial app download and every update. Check the platform's current documentation before choosing its on-demand asset mechanism.

Make cloud execution narrow

Send only the fields the operation needs. For classification, that may be identifiers, short titles and a few examples from existing groups. Full records, attachments and account history add unnecessary data. For a conversation, bound the recent context window.

Credentials belong behind an authenticated proxy, never in the app binary. The proxy should validate input type, length, count, and media size; verify app attestation where the platform supports it; enforce rate and entitlement policy; and translate provider errors into a stable application error vocabulary.

Choose retries by error type. An unauthenticated response may justify one authentication refresh. A timeout may arrive after inference has already been accepted and billed, so use an idempotency key where repeating the request could duplicate a cost.

Translate errors into messages and actions the user can understand. A backend resource_exhausted can become "try again later"; an offline state can offer a connectivity action. Malformed output should leave data unchanged or fail the review step. Keep provider error strings out of the customer interface.

Converge at the validation layer

Local and cloud implementations don’t need identical prompts or APIs. They need equivalent domain behaviour. Once each route has produced decoded transport types, everything runs through one shared pipeline:

  1. Validate identifiers against the set that was submitted.
  2. Normalise enum values, whitespace, dates, and currency codes.
  3. Reject impossible numbers and unsafe links.
  4. Convert the result into a proposal the user can review.

Each adapter extracts any JSON region and decodes its transport types before entering this shared pipeline. The common validator then applies the same persistence rules to both routes. An unknown group in a cloud response or a missing item in a local response must leave the original data unchanged.

For a received batch response, preserve input order and produce one decision per item. Missing or malformed entries become explicit keep decisions. A transport failure for an entire chunk is different: retain the successful chunks and leave items in the failed chunk pending for retry. If every chunk fails, report a service error. Marking those items as keep would wrongly suggest that the service had checked them and found no changes necessary.

Design the UX around uncertainty

Show useful status such as "Preparing on this device" rather than vendor-specific errors. When automatic routing sends data off-device, make that clear, especially for a feature described as local.

Let the user review generated changes as a before/after diff, a selectable plan or an editable extraction. Save only accepted changes. That keeps the original intact when either route fails.

Store the in-flight task. Cancel it when the sheet disappears and before starting a replacement. Cooperative cancellation alone does not prevent a late result from arriving, so check a generation token before applying it:

generation += 1
let mine = generation
work?.cancel()
work = Task {
    do {
        let proposal = try await service.classify(snapshot)
        try Task.checkCancellation()
        guard mine == generation else { return }
        state = .review(validate(proposal, against: snapshot))
    } catch is CancellationError {
        // expected on replacement — do nothing
    } catch {
        guard mine == generation else { return }
        state = .failed(localize(error))
    }
}

If the user switches modes while a slower route is running, only the matching generation can update the screen. The catch block also reports failures instead of leaving a spinner active. This example assumes a single isolation context, such as the main actor, for access to the state.

Observe decisions without observing users

Record the operation, the route, the decision reason, the availability state, a duration bucket, the validation outcome, and an error class. Do not record raw prompts, image contents, account text, or model output. An allow-list for analytics properties is safer than hoping everyone remembers what not to log, and free-text diagnostic fields should be redacted before upload.

Use this telemetry to measure local unavailability, automatic fallback to cloud, validation failures by language and abandonment during model preparation. Base routing policy changes on measurements from the deployed app.

Executable scenarios

Write these as tests and adapt them to your own domain.

Automatic mode respects local capability. Given a short rewrite, a ready on-device model, and no need for external data, when the resolver runs, then it picks the local service as primary. Cloud entitlement is checked only to decide whether a cloud fallback may be offered.

Local-only means no upload. Given the user chose on-device-only mode and the model assets are unavailable, when a classification is requested, then the app reports that local capability is unavailable and makes no cloud request.

Automatic fallback requires consent. Given local execution fails with a recoverable error and cloud is technically available, when upload consent has not been granted, then the app asks for consent or stops without transmitting the input.

Both routes enforce identifier membership. Given either implementation returns a suggestion referencing an identifier absent from the request, when the validator processes it, then that suggestion becomes “keep unchanged” and cannot reach persistence.

A late result cannot replace a newer one. Given request A is running and the user switches mode, starting request B, when B completes first and A completes later, then only B’s matching generation may update the review state.

When this is not worth it

A runtime router is overkill when a feature has one safe execution environment, low device heterogeneity, low volume, and no meaningful difference in privacy, capability, or marginal cost. A simple provider-neutral protocol with a single implementation is enough. Don’t add a local model just to claim “offline AI” if deterministic logic solves the task more reliably.

Use hybrid execution when device eligibility varies, cloud cost affects the product, upload consent restricts a route, or operations need different capabilities. Keep those decisions together in the router so each request follows the same product rules.
