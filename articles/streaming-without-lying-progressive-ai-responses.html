Streaming without lying.

Let users see a response as it arrives. Keep actions disabled until the complete result has passed validation.

By Asım Can Yağız8 September 2026Updated 16 November 20267 min read

The pattern

  1. Two clocks, one response
  2. Show the surface, gate the action
  3. Structure makes it non-negotiable
  4. Cancellation is part of streaming
  5. Failing mid-stream cleanly
  6. Model it as a state machine

Streaming can make an AI feature feel faster without shortening the request. Users see tokens arrive while the model is still working, instead of waiting for a blank screen to fill.

The difficulty starts when that preview controls an action. A structured response cannot pass validation until it is complete. If the app enables Save or Apply while tokens are still arriving, it lets the user act on data it has not checked.

I separate the preview from the result the application can use. Text can appear progressively, but a partial response must not change stored data or trigger a paid operation. The interface needs to make that provisional status clear.

1. Two clocks in one response

Measure first useful output separately from completion and validation. The first tells you when there is something worth showing. The second tells you when the whole response is present, parses successfully and meets the output contract.

A Save button, a state change or a paid side effect belongs after the second event. If it runs after the first, later tokens can change the meaning of data the app has already used. The response might also fail to parse or be cut short by a safety filter.

Principle 01

Separate what you show from what you trust. The display path can be optimistic; the commit path waits.

2. Show the surface, gate the action

Split the response into what the user may see while it streams and what the app may do only after it validates.

Render the text as it arrives. Keep Apply, Save, Send, Purchase and any other control that changes state disabled until the complete response has parsed and passed validation.

Stream→Complete→Validate→Commit→Action

Once validation succeeds, enable the action and reconcile the preview with the validated result. They will usually match. When they differ, replace the preview before the user can act on it. This preserves the benefit of seeing progress without letting provisional data affect the rest of the app.

3. Structure is what makes this non-negotiable

Display-only prose does not carry the same risk of committing incorrect application state. An object containing an action, an amount and a list of targets does. Wait for the closing brace and validate the whole object. Partial JSON may fail to parse; a lenient parser may accept it and produce an incorrect object.

For progress during a structured response, use a separate text field explicitly marked as partial. Do not drive actions from a partial parse of the machine-readable object. If parsing or validation fails at completion, treat the response as failed.

4. Cancellation is part of streaming, not an afterthought

A user can leave the screen, background the app, edit the input or start another request while a stream is running. The app needs a rule for deciding which request is still current.

Give each request an identifier. When the user cancels or starts a replacement, mark the old stream stale. Discard any further tokens from it. If it completes later, record the discard under its request id and neither present nor commit its result. Only the current request can supply a completed, validated result to the interface.

5. Failing mid-stream without leaving a mess

A connection can drop after some tokens arrive. A provider can return an error or a safety filter can stop the response. The preview is then incomplete, and the app needs to recover:

  • Mark the preview as provisional until commit. If the response fails, discard the preview and show a failure or fallback.
  • Commit nothing. No structured data, no side effect, because the response never validated.
  • Make recovery a real state, not an exception swallowed into a spinner that never ends.

Use idempotency for side effects as well. Retrying after a stream fails must not apply the same change twice or charge twice. Tie the effect to the completed, validated commit.

6. Model it as a state machine

Separate booleans such as isStreaming, isDone and hasError can represent contradictory states. A state machine makes the allowed transitions explicit and gives telemetry something consistent to record:

Watch the discarded rate to see whether users routinely move on before a request finishes. Also track failures during validation: a stream can look healthy while it is arriving and still fail the output contract at the end.

Behavioural tests

  • Given a streamed structured response still in progress, when the user views it, then a progressive preview renders but every consequential action stays disabled until the full response validates.
  • Given a stream that fails contract validation at completion, when a preview was already shown, then the app discards the preview, commits nothing, and shows a clear failure or fallback.
  • Given the user starts a new request or cancels mid-stream, when the older stream completes later, then its result is neither presented nor committed, and the discard is recorded under the same request id.
  • Given partial structured output arriving token by token, when the app parses, then it tolerates incompleteness, acts on nothing until a complete valid parse, and never drives a side effect from a partial object.

When this is not worth it

For a short response, waiting for completion and rendering once may be simpler. Display-only text with no downstream action does not need the same commit controls. Use the full state machine when responses are structured, trigger actions or charges, or appear in a screen where users often cancel and start again.
